# 架构

## 一句话

宿主侧是一个 macOS 应用 + 一个进程内编排层；每个实例对应一个 `qemu-system-aarch64` 子进程；两者之间只有 socket，没有函数调用。

## 分层

```
┌─────────────────────────────────────────────┐
│ SwiftUI 壳（app/）                           │  实例列表、按钮、画面预览
├─────────────────────────────────────────────┤
│ AndroPodCore（Swift）                        │  QMPClient、FramePoller、Workspace
├─────────────────────────────────────────────┤
│ engine/andropod（Python，阶段 0）             │  实例编排、命令行、快照
├─────────────────────────────────────────────┤
│ qemu-system-aarch64（独立进程，未修改）        │  ← GPLv2 边界
├─────────────────────────────────────────────┤
│ 客户机：Alpine arm64（临时）/ Android arm64   │
└─────────────────────────────────────────────┘
```

Python 引擎是阶段 0 的产物，目的是用最短路径验证 QMP 编排。产品化时它会被 `AndroPodCore` 里的 Swift 实现取代——协议不变，只是换宿主语言。把它当作**可执行的协议规范**来读，而不是最终架构。

## 为什么一个实例一个进程

- 崩溃隔离：一个实例的 QEMU 段错误不该带走整个应用
- 资源可回收：杀掉进程就等于归还全部内存，统一内存架构下这点很关键
- 多开配额：可以给每个进程单独做 CPU/内存上限

代价是启动开销（实测 0.13s，可接受）和状态同步复杂度（用 pid 文件 + QMP 双重确认）。

## 为什么两条 QMP 通道

QMP chardev 是单客户端：一个 socket 同时只能有一个连接，第二个连接会被拒绝。

UI 需要持续抓帧，就必须长期占用一条连接。于是给 QEMU 传两次 `-qmp`：

- `qmp.sock` —— 控制面（启动检查、快照、停止）
- `qmp-display.sock` —— 显示面（抓帧循环）

已验证 QEMU 11 支持多个 `-qmp`，且两条通道可同时在线。

## 启动路径：直接内核引导

实例不经过固件和引导器，直接用 `-kernel` / `-initrd` / `-append` 引导：

```
-machine virt,accel=hvf -cpu host -kernel vmlinuz-virt -initrd initramfs-virt
```

好处：
- 启动路径短且确定，没有 UEFI 和 bootloader 的不确定性
- 不挂 CD-ROM，所有块设备都是 qcow2，**全量状态快照才可能成功**（raw 设备不支持内部快照）

安卓镜像最终也会走这条路（`emulator` 自己就是 `-kernel kernel-ranchu + ramdisk` 的模式）。

## 显示路径

当前：QMP `screendump` 反复抓 PNG 帧 → `NSImage` → SwiftUI。

- 优点：几十行代码，端到端可验证，PNG 只有 3 KB/帧
- 缺点：只读，不能注入输入；10 fps 上限；每帧一次磁盘往返

**这不是最终方案**。真正的产品需要双向像素流 + 输入注入，路线是内嵌 RFB/VNC 客户端（QEMU 的 `-vnc` 是独立端口，不占 QMP），或者更彻底的共享内存显示通道。`FramePoller` 是个占位实现，接口刻意做窄，方便整体替换。

## 健康检查的坑

判断进程存活不能用 `ps`（受限环境下不可用），也不能只用 `kill(pid, 0)`（僵尸进程仍然返回成功）。

正确做法：
- 手里有 `Popen` 句柄时 → `poll()`，它同时完成回收
- 跨进程时 → `kill(pid, 0)`，此时子进程已被 launchd 收养，不会留僵尸

跨进程场景还要处理**残留 pid 文件**：进程被强杀后 pid 文件还在，下次启动会误判"已在运行"。`_clear_stale_state()` 在启动前清掉这类残留。
