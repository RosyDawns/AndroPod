# 许可边界（GPLv2）

这不是法律意见，是工程上必须遵守的自查清单。真正上线前请找律师过一遍。

## 问题在哪

QEMU 是 **GPLv2**。GPLv2 的传染性针对「衍生作品」（derivative work）。如果把 QEMU 当成库链接进闭源产品，整个产品都要开源。

我们的做法是**不做衍生作品**：QEMU 是一个独立进程，我们通过它公开的线协议驱动它。

## 六条硬规矩

1. **不 import、不 link、不静态库。** 项目里任何代码都不得包含 QEMU 头文件或链接 QEMU 目标文件。
2. **只 `exec` + socket。** 交互仅通过 QMP、ADB、VNC 等公开协议。本项目当前的实现即 `engine/andropod/qmp.py` 与 `app/Sources/AndroPodCore/QMPClient.swift`——两者都只发 JSON，不共享内存结构。
3. **分发未修改的官方二进制。** 如果能做到零 patch，就不产生「修改版分发」的问题。需要随包提供对应源码的获取入口（官网放一个指向 qemu.org 对应版本 tarball 的链接即可满足 GPLv2 §3 的书面承诺）。
4. **你打的 patch 必须开源。** 一旦修改 QEMU 源码，修改部分必须是 GPLv2。建议直接放 GitHub，反而能变成社区资产。
5. **一个可执行文件里不能混 GPL 与闭源代码。** 不要做「静态把 QEMU 塞进 app bundle 然后一起签名」这种看起来方便、实际踩线的事。
6. **避开商标。** 「QEMU」是 QEMU 项目的商标，产品名、bundle identifier、UI 文案里都不要出现。

## 现在的实际状态

| 组件 | 许可 | 判断 |
|---|---|---|
| QEMU（Homebrew 安装，未修改） | GPLv2 | 开发期由用户自行安装，我们不分发，无义务 |
| Alpine 测试镜像 | 各自上游许可 | 仅开发期使用，不随产品分发 |
| `engine/`（本仓库） | 待定，建议 MIT/Apache-2.0 | 自有代码 |
| `app/`（本仓库） | 待定 | 自有代码 |

**当前阶段没有任何 GPL 义务**：我们不分发 QEMU，只要求开发者自己 `brew install`。

一旦要做商业分发，第 3 条才开始生效。

## AOSP 这块相对干净

AOSP 主体是 Apache-2.0，可商用、可闭源定制，保留版权声明即可。

但注意：
- **GMS / Google Play 不能预装**。Google 的授权不允许第三方镜像打包，MuMu、BlueStacks 都是让用户自己装。
- 部分国内应用商店和游戏有独立的商业分发协议，需要单独谈。
- 安卓系统镜像里如果混入了厂商闭源驱动，会引入新的许可问题。

## 一个常被忽略的点

「独立进程 + IPC」是业界常见做法，但**不是法律上的免死金牌**。判定取决于你改了多少、耦合有多深、IPC 是否只是规避手段。

降低风险的实际动作，按性价比排序：

1. 不改 QEMU 源码（最有效）
2. 不改就用官方发行版，别自己编
3. 真要改，把 patch 开源
4. 咨询律师

前两条做到了，实务上基本没有争议。
